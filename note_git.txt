The Professional Git Workflow (day-to-day)
Think of Git work in 5 phases:
1) Sync → 
2) Branch → 
3) Work → 
4) Review → 
5) Merge
NOTE:
1) Start your day: Sync with main branch
Always begin by updating your local repo.
TODO: git checkout main
TODO: git pull origin main
Why?
Avoid working on stale code
Reduce merge conflicts later
Many devs do this every morning.

2) Create a feature branch
Never work directly on main.
Branch naming usually follows ticket numbers.
Examples:
feature/login-api
fix/payment-timeout
refactor/cache-layer
chore/update-deps

Create branch:
TODO: git checkout -b feature/my-task-name
You are now isolated from the main branch.

Check branch:
TODO: git branch
TODO: git branch -vv

3) Do the work (daily loop)
Edit → stage → commit (repeat many times)
Check changes:
TODO: git status
TODO: git diff
Stage files:
TODO: git add .
(or selectively)
TODO: git add file.py
Commit:
TODO: git commit -m "Add validation for email field"
Good commit message style
Professionals write clear, atomic commits.
Format often used:
<type>: short description
Examples:
feat: add login endpoint
fix: handle null pointer in parser
refactor: simplify retry logic
test: add unit tests for auth service
Rule of thumb:
One commit = one logical change.

Conventional Commits:
TODO:<type>: <short summary>
feat: new feature
fix: bug fix
refactor: code cleanup
test: tests
docs: documentation
chore: maintenance
Example:
feat: add login API
fix: handle null pointer crash
refactor: simplify retry logic

4) Keep your branch up-to-date (VERY important)
While you work, main branch keeps moving.
Every day or two:
git fetch origin
git rebase origin/main
Why rebase instead of merge?
Keeps history clean
Avoids messy merge commits
Resolve conflicts if needed:
# fix files
TODO: git add .
TODO: git rebase --continue
This step is core professional habit.

5) Push your branch to remote
TODO: git push origin feature/my-task-name
First push usually:
TODO: git push -u origin feature/my-task-name

6) Open a Pull Request (PR)
On GitHub/GitLab/Bitbucket:
Explain what
Explain why
Link ticket
Typical PR description:
## What
Add email validation to signup API
## Why
Prevent invalid users from entering system
## Test
- Unit tests added
- Manual tested via Postman

7) Code review cycle
Reviewers will:
Comment
Request changes
You update code and push again:
TODO: git add .
TODO: git commit -m "Address review comments"
TODO: git push
PR auto-updates.

8) Merge the PR
After approval:
Squash & merge OR
Rebase & merge
Then cleanup locally:
TODO: git checkout main
TODO: git pull origin main
TODO: git branch -d feature/my-task-name
Branch lifecycle complete 🎉

Golden Rules of Professional Git
1) Never commit to main directly Ever.
2) Commit small and often
Huge commits = nightmare reviews.
3) Rebase frequently
Conflicts grow exponentially with time.
4) Write meaningful commit messages
Future you will thank present you.
5) Pull before you push
Avoid breaking CI.

Bonus: Advanced habits senior engineers use
Interactive rebase to clean history:
git rebase -i origin/main
Stash temporary work:
git stash
git stash pop
Fix last commit:
git commit --amend
Undo staged files:
git reset HEAD file.py


情境：最新 commit 壞掉了 → 想回到上一版。
先講重點：
👉 可以回上一版
👉 不一定會刪掉最新版本（看你用哪個指令）
Git 有 2 大流派：
安全回退（保留歷史）✅公司常用
強制回退（改寫歷史）⚠️個人用
🟢 方法1：安全回到上一版（公司最推薦）

用 revert
TODO: git revert HEAD
這個指令做的事：
產生一個「新的 commit」
把上一個 commit 的改動全部反向套用
歷史會變成：
A --- B --- C (壞掉)
           ↓
A --- B --- C --- D (revert C)
👉 最新壞掉的版本 還在歷史裡
👉 但程式碼已回到上一版
公司為什麼愛用？
不會改寫歷史
不會害隊友爆炸 💣
答案：最新版本不會被刪除

🔵 方法2：本地回到上一版（最常用）
如果你只是本地還沒 push：
TODO: git reset --soft HEAD~1
回到上一版，但保留修改在 staging。
或：
git reset --mixed HEAD~1
回到上一版，修改留在 working directory。
或最狠：
git reset --hard HEAD~1
效果：
A --- B --- C (壞掉)   ❌被砍掉
↓
A --- B
👉 最新 commit 直接消失
⚠️ 只有在 沒 push 時能安全用！
